KPI API

Deliver Provider-scoped Balanced Scorecard, goals, targets, rankings, scorecards, workflow states, and trend data.

API-DOC-012
Version

Status
Draft
Last Updated

Purpose

Deliver Provider-scoped Balanced Scorecard, goals, targets, rankings, scorecards, workflow states, and trend data.

Security, privacy, and proprietary workflow notice

The KPI API may process PHI, workforce data, payroll information, Provider identifiers, EVV evidence, location data, or administrative records. Public examples use demonstration values. Production credentials, tokens, private routes, customer data, and proprietary validation details must remain restricted.

Functional Scope

The KPI API provides the backend contract for the related True Care System workspace. The API is responsible for Provider isolation, role authorization, input validation, business-state enforcement, safe response shaping, and applicable audit evidence.

Primary Endpoint Groups

MethodRouteGeneral Purpose
GET/kpi/bscReturn the Provider Balanced Scorecard.
GET/kpi/strategy-mapReturn mission, vision, perspectives, and strategy relationships.
GET/kpi/goalsReturn strategic goals and targets.
GET/kpi/rankingsReturn perspective, department, manager, or employee ranking data.
PATCH/kpi/scorecards/:idUpdate an authorized scorecard item.

Request and Authorization Controls

  • Require a valid authenticated session for protected routes.
  • Resolve Provider scope from trusted server-side identity context.
  • Apply role and action permission checks before data access.
  • Validate route parameters, query filters, dates, statuses, and request bodies.
  • Prevent cross-Provider access and avoid disclosing whether out-of-scope records exist.
  • Record applicable view, create, update, delete, approve, submit, export, or impersonation activity.

Example Request

GET /api/kpi?page=1&limit=25
Authorization: Bearer <access-token>
Accept: application/json

Example Success Response

{
  "success": true,
  "message": "KPI data returned.",
  "data": {
    "items": [],
    "page": 1,
    "limit": 25,
    "total": 0
  },
  "requestId": "demo-request-id"
}

Common Error Conditions

ConditionExpected handling
UnauthenticatedReturn an authentication error without exposing account details.
Forbidden roleReturn a forbidden response and preserve security-relevant evidence where required.
Cross-Provider identifierReject access without confirming the existence of the external record.
Invalid inputReturn safe field-level validation details.
Invalid state transitionReject workflow actions that do not meet readiness, approval, status, or effective-date requirements.
Unexpected failureReturn a generic error and request ID while storing diagnostics only in protected logs.

Audit and HIPAA Expectations

Where a request accesses or changes PHI or sensitive operational information, the system should preserve the authorized Provider, user or actor, target record, module, action, timestamp, request context, purpose of use where applicable, minimum-necessary status, outcome, and approved metadata.

Implementation Checklist

  • Route and controller contract documented.
  • Request DTO or schema validation implemented.
  • Provider filter enforced in business logic and data access.
  • Role authorization verified.
  • Sensitive response fields reviewed.
  • Audit behavior verified.
  • Success, validation, forbidden, not-found, conflict, and failure cases tested.
  • QA Guide and Test Catalog updated.

Troubleshooting

No records returned

Review Provider scope, date range, filters, status, pagination, user role, and record readiness.

Forbidden response

Confirm the user's assigned role and permission. Do not bypass backend guards or replace the Provider identifier.

Validation failure

Compare the payload with the approved DTO, required fields, effective dates, enum values, and workflow state.

Unexpected server error

Use the request identifier to locate protected server logs. Do not expose stack traces, secrets, or raw database errors to the client.
